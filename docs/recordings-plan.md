# Phase 3: My Recordings (private personal set videos)

Status (2026-11-22): **migration `20261011002000_personal_recordings.sql` applied (owner-approved); R2 bucket configured; feature on branch `phase-3-recordings`, not merged or deployed.** Until `R2_*` is configured on a deployment, the feature is fully hidden there (no UI, no requests).

## Owner decisions (2026-11-22)
- **Storage:** Cloudflare R2, private bucket.
- **Quota:** 250 MB per user on Free (was 500 MB until migration 0022, 2026-11-22); 5 GB planned for Pro. No subscription system yet, so everyone is on Free.
- **Limits:** 90 seconds maximum per recording; 100 MB maximum original upload.
- **Capture:** record directly or upload from the camera roll.
- **Attach to:** an individual set, or the exercise.
- **Shown in:** exercise history (the My Recordings section on the exercise page).
- **Privacy:** private by default.
- **At the limit:** further uploads are blocked. Recordings are never deleted automatically.
- **Proof videos:** leaderboard proof videos stay separate for now.

## Architecture

```
Browser ──(1) begin_recording via server action──► Supabase: validate, lock the user's account row, check quota, reserve bytes, random key
        ◄──── 15-minute presigned PUT (exact Content-Length + Content-Type signed) ─── server (R2 keys never leave it)
        ──(2) PUT file straight to R2 (XHR: progress, cancel, retries) ──► private R2 bucket
        ──(3) finish via server action ──► server: HEAD (real size) + ranged GETs (signature, real duration from the
                                           MP4/MOV movie header or WebM info) → finalize_recording (secret key) → ready
Playback: server action → RLS says it's yours → 10-minute presigned GET → <video preload="metadata">
```

- **Supabase** holds metadata only: `personal_recordings` (owner, exercise, optional set, session + draft row while a workout is in progress, object key, type, reserved and actual bytes, real duration and resolution, title, note, dates), `storage_plans` (`free` 250 MB, `pro` 5 GB), `video_storage_accounts` (per-user plan; the row each reservation locks), and `recording_object_deletions` (the R2 cleanup queue).
- **R2** holds the files under `rec/<32 random hex>.<ext>`: no user id, no exercise, not derived from the row id. Keys are generated by the database and re-checked by the server before any URL is signed.
- **Plans:** a user's quota is `storage_plans.quota_bytes` for their account's `plan_id` (default `free`). Pro later = set `plan_id = 'pro'` server-side (a billing webhook); no schema change. Users have no write access to plans or accounts.

## R2 setup (owner, 2026-11-22)
- Private bucket `sblift-recordings`: no public access, no r2.dev URL, no custom domain.
- CORS: `PUT`, `GET`, `HEAD` from `https://liftrank-roan.vercel.app` and `http://localhost:3000`; allowed header `content-type`; exposed `etag`; max age 600 s.
- API token: Object Read & Write on that bucket only (it can't list the account's buckets).
- Server-only env (`.env.local` and Vercel Production; never `NEXT_PUBLIC_`): `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`. `R2_ACCOUNT_ID` may be the bare 32-hex ID or the endpoint Cloudflare shows (`https://<id>.r2.cloudflarestorage.com`); anything else leaves recordings off (`r2Endpoint`). `R2_ENDPOINT` is only for the local stand-in.

## Security
- RLS: owner-only `select` on recordings and accounts; **no insert/update/delete grants**. Every write goes through SECURITY DEFINER functions (`search_path = ''`, `auth.uid()`, never a user id argument for user-callable ones).
- `finalize_recording` and the cleanup functions are executable **only by `service_role`**. The server calls finalize with the secret key, for the signed-in caller's own recording, only after checking the stored object itself. A user can't mark an upload ready, change its size, or skip the checks.
- Everything the client says is validated: the exercise exists, a set is theirs **and** of that exercise, a session is theirs (and active for a draft row), size 1 B–100 MB, type MP4/MOV/WebM, duration ≤ 90 s. Then the stored file is re-checked: actual size ≤ reserved (else rejected and removed), file signature matches the declared container, and the **real** duration is read from the file (≤ 90.5 s). Extensions and browser types are never trusted alone.
- Upload URLs: 15 minutes, for one key, exact size and type (tampering → 403). Playback URLs: 10 minutes, GET only, `inline` with the stored type. Unsigned access to the bucket → 403. The bucket must **not** have public access or an r2.dev URL.
- No one can overwrite another user's file: keys are random and database-issued, and each upload URL is signed for one key.
- Recordings never appear on profiles, friends' activity, boards, notifications or proof flows (no code path reads them there; Flow S checks lifts and notifications stay empty).

## Quota and accounting
- Usage = sum of `bytes` of ready recordings (their **actual** stored size) + `reserved_bytes` of live pending uploads. It's computed from the metadata rows under the user's account-row lock; no R2 listing, ever.
- `begin_recording` locks the user's account row (`select … for update`) before checking `used + reserved + new ≤ quota`, so concurrent uploads are decided one at a time and can't overshoot. At most 4 uploads in flight per user, 60 per day.
- Reservations are released on cancel, failure, rejection, and after 30 minutes (lapsed). Lapsed ones never count; they're deleted lazily on the next upload and by the daily job.
- Deleting a recording frees its space immediately.
- Full storage: `storage_full` before anything is uploaded, explained in plain words ("Delete recordings you no longer need in Settings → Video storage"). Nothing is ever deleted automatically.

- **Shrinking an allowance** (0022: Free 500 → 250 MB) is one row in `storage_plans`. Nothing is deleted: a user over the new allowance keeps every recording, Settings says they're over it, and `begin_recording` refuses uploads until used + reservations + the new file fit again. Concurrency is unchanged (per-user lock); `scripts/check-quota-concurrency.mjs` checks it against the hosted DB with a throwaway user on a temporary test plan.

## Cleanup
- Any recording row that goes away (deleted, cancelled, failed, lapsed, or its owner's account deleted, via cascade) queues its key in `recording_object_deletions` (trigger).
- The daily cron (`/api/cron/daily`) calls `recording_maintenance()` and deletes queued keys from R2, then `recording_objects_removed(keys)`. Keys are handed out only after 20 minutes, longer than any upload URL lives, so a late upload can't re-create a file after cleanup.
- Deletes and cancels also remove the R2 object right away (best effort); the queue is the guarantee.
- Account deletion removes the user's R2 objects immediately (`my_recording_keys`) and the cascade queues them again as a backstop.

## Training integration
- **During a workout:** each exercise's ⋯ menu → "Add recording…" → choose a set row (with what you've typed) or the whole exercise → Record video / Upload video. Rows with a recording show a small camera mark; no thumbnails in the logger.
  - The recording points at the draft row (`session_id` + `draft_ref` = "block/row"). End (`finish_training_session`, redefined with one addition) links it to the saved set in the same transaction. Rows left empty → the recording stays on the exercise.
  - Uploads run in the app shell (`UploadProvider`), so typing, autosave, tab switches and End are never blocked. End while an upload is pending works: the link is made at End, and the file finishes afterwards.
  - Removing a set or an exercise, or discarding the workout, asks: keep the recording(s) on the exercise, or delete them. Never silent.
- **After a workout:** the exercise page's My Recordings → "Add recording" (your recent sets with date, weight, reps and RIR), or a completed session page → "+ Recording" next to each exercise (that session's sets).
- **Change association later:** Edit → Set (any of your sets of that exercise, or "No specific set"). No re-upload.
- Deleting a set in history asks whether to keep its recording (on the exercise) or delete it too. The foreign key never deletes a recording (`on delete set null`).

## Upload reliability (and limits)
- Progress per upload, cancel, automatic retries (up to 4 tries with backoff; an expired URL is renewed while the reservation lasts), "Retry" for recoverable failures.
- "Saved" is shown only after the server verified and finalized the file.
- **Limitation:** a browser upload can't outlive the page. Closing or reloading the tab stops it (the app asks before you leave while one is running). The reservation lapses after 30 minutes and the row shows as "Upload interrupted" with Remove; upload the file again. True background upload needs a native app (see `docs/ios-packaging.md`).

## Compression
- **Decision for now: no transcoding.** Files are stored as recorded and count at their real size.
- iPhone records HEVC by default (~60 MB/min at 1080p30), so a 90 s 1080p clip fits under 100 MB. 4K or 60 fps clips longer than ~30–45 s won't; the app says so and suggests 1080p or trimming. iOS Safari may already re-encode a camera-roll pick to a smaller H.264 file.
- Options considered:
  - **Server-side transcode** (Cloudflare Stream or Media Transformations, or ffmpeg on a worker): consistent 720p H.264 (~10–20 MB per 90 s), but per-minute cost and a new service with webhooks. Worth revisiting if storage, not count, becomes the limit.
  - **Client-side transcode** (WebCodecs + an MP4 muxer): free and private, but uneven on iOS Safari (VideoEncoder from 16.4, slow on older phones, drains battery during a workout).
- Playback: H.264 MP4 plays everywhere; HEVC plays in Safari and on iPhone, not in some desktop Chrome/Firefox builds (the player says so).

## Performance
- No video bytes on any page load. The exercise page fetches 12 recordings' metadata (plus which sets have one) in parallel with its existing query, only when recordings are enabled. "Show more" pages by date.
- The Training logger loads one small list (this session's recordings) once, after it renders. Day switching, the exercise picker and startup are unchanged.
- Settings → Video storage: one usage RPC plus 12 rows of metadata.

## Upload performance (measured 2026-11-22)
`tests/e2e/upload-perf.spec.ts` (opt-in, `E2E_UPLOAD_PERF=1`) times each stage from the browser's real requests. The files mimic iPhone recordings: QuickTime, with the movie header at the end.

| File | Client prep | Reserve | PUT to storage | Verify (server) | Total |
|---|---|---|---|---|---|
| 10 MB (real R2) | ~0 s | 0.13 s | 7.2 s | 1.5 s | 9.4 s |
| 30 MB (real R2) | ~0 s | 0.22 s | 20.1 s | 1.3 s | 22.0 s |
| 60 MB (real R2) | ~0 s | 0.25 s | 46.2 s | 2.0 s | 48.8 s |
| 90 MB (real R2) | ~0 s | 0.24 s | 55.6 s | 1.7 s | 57.9 s |
| 10–90 MB (local stand-in) | ~0 s | 0.13–0.22 s | 0.04–0.14 s | 0.4–0.7 s | 0.8–1.3 s |

- **The bottleneck is upload bandwidth × file size.** This Mac uploaded to R2 at 11–14 Mbit/s, and the transfer is 77–96% of the wait. With the network removed (stand-in), the app's own work is about 1–1.3 s at any size.
- **Measurement limits:**
  - These runs were from a desktop on home Wi-Fi; phones on cellular are often slower and more variable.
  - Server verification here ran from this Mac to R2, so on Vercel it should be similar or faster.
  - Client prep was measured in Chromium with synthetic files. Reading metadata of a real HEVC file on an iPhone wasn't measured (no device here).
- **Changes made:**
  - Verification gets the stored size and the file's first bytes in one ranged GET (R2 returns the total in `Content-Range`) instead of a HEAD plus a read. That's one fewer round trip, and it's as trustworthy, since both come from R2.
  - The in-browser duration check waits at most 1.5 s, down from 4 s, before the upload starts. It's early feedback only; the server always reads the real duration.
- **What would actually speed it up (owner decisions):**
  1. **Smaller files at the source.** iPhone *Settings → Camera → Record Video → 1080p at 30 fps* is about 60 MB per minute in HEVC; 4K/60 is several times that. A one-line hint in the Add recording sheet when a file is over about 60 MB is free.
  2. **Optional on-device compression** (WebCodecs + an MP4 muxer) to about 720p before upload: 3–6× smaller. Trade-offs: CPU and battery during a workout, uneven support on older iPhones, and a re-encode before the upload can start. Opt-in only.
  3. **Server-side transcoding** (Cloudflare Stream or Media Transformations, or a worker running ffmpeg) doesn't make the upload itself faster; it only shrinks storage. Not recommended for speed, and it would be a paid service.
  4. **Parallel or multipart uploads** don't help a single phone limited by its own uplink. Skip.

## On-device compression: investigation (2026-11-23, not implemented)
**Idea:** before uploading, re-encode the clip on the phone to a smaller, widely playable file, for example 720p (or 1080p) H.264 at a modest bitrate, and upload only that.

**How it would work**
- The browser's own video encoder (WebCodecs) does the work, driven by a small MP4 library (Mediabunny: zero-dependency, MP4 in and out, uses the hardware encoders).
- Everything happens in a background thread inside the page, streaming the file so it's never all in memory.
- The library is loaded only when someone compresses, so there's no cost to normal page loads.
- The audio track is copied unchanged (AAC passthrough), not re-encoded.
- The result is an ordinary MP4. Server verification (real size, container, duration) is unchanged, and the original never leaves the phone.

**Compatibility**
- **iOS Safari:** the video encoder is partial on 16.4–18.x and full from iOS 26 (caniuse). Re-encoding audio needs iOS 26, hence the copy.
- **HEVC:** hardware HEVC encoding through the browser encoder isn't documented for iOS, so the target is H.264. That has a bonus: H.264 plays in every browser, fixing today's "HEVC won't play in some desktop browsers" gap.
- **Fallback:** an unsupported device, or any failure mid-way, uploads the original as today. Compression is never required.
- **Orientation:** iPhone files store rotation as metadata, which the compressor must carry over or apply (a common bug to test for).

**Quality**
- 720p H.264 at about 2.5–3 Mbit/s (≈19–23 MB per minute) is plenty for checking form: bar path, depth, joint angles. 1080p at about 5 Mbit/s (≈38 MB per minute) keeps more detail.
- **Generational loss:** a re-encode of an already-compressed phone clip loses some fine detail and can blur fast motion slightly. It's visible side by side, rarely for form review.
- **No savings without downscaling:** converting 1080p HEVC to 1080p H.264 at a similar quality makes the file *bigger*, since HEVC is more efficient. The savings come from resolution and bitrate, not the codec.

**Speed**
| Source clip (90 s) | Size now | After 720p H.264 | Upload at 12 Mbit/s: now → after |
|---|---|---|---|
| 1080p30 HEVC (iPhone default) | ≈ 90 MB | ≈ 30 MB | 60 s → 20 s |
| 4K30 HEVC | ≈ 250–300 MB (over the 100 MB limit today) | ≈ 30 MB | can't upload → 20 s |
| 720p already, or a short clip | small | little change | not worth it |

- **The encoding itself takes time.** Hardware encoding on recent iPhones is expected to run faster than real time, but there are no published iPhone benchmarks for this path. Assume roughly 15–45 s for a 90 s clip until measured.
- **So it only pays off when the upload is slow or the file is big.** On fast Wi-Fi, a 90 MB file uploads in under 10 s and compressing first would be slower.
- **Cost:** heavy CPU and GPU use warms the phone and drains battery mid-workout. Like uploads, it stops if the app is backgrounded (iOS suspends pages), so it adds foreground time.

**Recommendation (if approved)**
- **When:** an opt-in "Make video smaller before upload" switch in Settings → Video storage, plus automatic use only for files that would otherwise be refused (over 100 MB, e.g. 4K).
- **Output:** 720p by default; 1080p optional.
- **Visibility:** the progress tray shows "Compressing…" then "Uploading…", with Cancel for either.
- **Before shipping:** measure on 2–3 real iPhones (encode time, battery, size, playback), verify rotation, and test failure fallback. Ship behind the switch first.
- **Safeguards unchanged:** quotas, private storage, signed URLs and server-side verification stay exactly as they are; the server still checks the stored file it receives.
